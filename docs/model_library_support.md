# CoolSolve Support for the Model Library

The [CoolSolve Library](https://github.com/IntSusEnergySystems/CoolSolve_Library)
gathers hundreds of thermodynamic models written in the EES language. This page
specifies **how CoolSolve integrates that library** and collects what CoolSolve
still needs to run its models:

1. the integration design (§2): a **snapshot of the library embedded in the
   CoolSolve binary at compile time**, an **HTML model explorer** in the GUI,
   and the **import of functions and procedures from any `.eescode` file**
   (no `.lib` files);
2. the list of features with their implementation plan (§3);
3. the **gap register**: EES features that are missing or behave differently in
   CoolSolve, found while converting library models (§4), with the bugs found
   on the way (§5).

The register is filled by the people converting models (see
[ees_import.md](ees_import.md) and the library's `docs/model_workflow.md`):
each library model that cannot run lists the IDs of the gaps blocking it in
its `model.json` (`missing_features`), so the number of blocked models gives the
development priority. [`ees_vs_coolsolve.csv`](ees_vs_coolsolve.csv) remains the
exhaustive feature inventory; this page is the prioritised, library-driven view.

---

## 1. Design principles

- CoolSolve should read **native EES code**. Library models are kept in EES
  syntax; when CoolSolve differs from EES, the fix belongs in CoolSolve.
- A library model folder is a CoolSolve project folder ("the folder is the
  project", [GUI §7](gui.md)): `<model>.eescode`, `<model>.initials`,
  `coolsolve.conf`, companion tables `<model>-<table>.csv`, `<model>.sol`, plus
  `README.md`, `model.json` and `figures/`.
- **Each CoolSolve build carries the library as it was when it was compiled.**
  The desktop application works offline, the online demo serves exactly the
  same content, and the library version is part of the CoolSolve version.
- **Functions are shared through `.eescode` files.** Any `.eescode` file — a
  library model or a file of the user — can provide its `FUNCTION`s and
  `PROCEDURE`s to another model; no `.lib` files are needed.

## 2. Integration design

### 2.1 Build-time library snapshot (`CS-FEAT-LIB-EMBED`) — implemented

The GUI binary carries the library as it was when it was compiled. The details (and the CMake options) are in
[GUI §9.6](gui.md#96-library-embedding); in short:

- **Fetched like CoolProp**: `FetchContent` clones `IntSusEnergySystems/CoolSolve_Library` into
  `.fetchcontent_cache/` at configure time. The default `COOLSOLVE_LIBRARY_TAG` is `main`, so each `cmake`
  configure — and therefore `build_gui.sh`, `build_installer.bat` and a server rebuild — embeds the **latest
  pushed library**; a release pins a tag (`-DCOOLSOLVE_LIBRARY_TAG=<tag>`, recorded in `docs/versions.md`).
  `-DFETCHCONTENT_SOURCE_DIR_COOLSOLVELIBRARY=<checkout>` embeds a local checkout instead (library authors; the
  version string then carries `+local-changes` if it is dirty). `-DCOOLSOLVE_EMBED_LIBRARY=OFF` builds without
  library.
- **Re-embedded at every build**: the `coolsolve_library_snapshot` target hashes the allow-listed files and rewrites
  the generated source only when they changed.
- **What is embedded** (under the URL prefix `/library/`): `library.json`, `library.html`, `taxonomy.json`,
  `docs/taxonomy.md`, and in each model folder `README.md`, `model.json`, `*.eescode`, `*.initials`, `*-*.csv`,
  `coolsolve.conf`, `*.sol` and `figures/*.{png,svg,jpg,jpeg,webp}`. Never `sources/`, `tools/`, `templates/` or
  `work/`. The allow-list is written twice — `cmake/embed_library.cmake` and `EMBED_FILES` in the library's
  `tools/build_index.py` — and the build warns when the file counts differ.
- **Identity**: `coolsolve --version` prints `CoolSolve Library <commit>, snapshot <hash>`; the snapshot block of
  `library.json` (content hash, counts) and the commit are in `GET /api/v1/library/menu` and shown by the menu.
- **Size**: ≈ 7 MB → 38 MB of generated source, ≈ 6 s and ≈ 1 GB of memory to compile on GCC, ≈ 8 MB more in the
  binary. If hex arrays prove too heavy for a compiler (to be checked with MSVC), split the arrays over several
  files or embed one packed archive behind the same lookup function.

All accesses go through one C++ `LibraryStore` (`include/coolsolve/library_store.h`: menu, loading of a model
folder, `embeddedLibrary()` for the snapshot of the binary), used by the server and by the `$INCLUDE`
resolution of the parser (§2.3), in the GUI and in the CLI.

**Not implemented yet**: a run-time override (`--library-dir <path>` / `COOLSOLVE_LIBRARY_DIR`) serving a checkout
from disk, so that library authors need no rebuild.

### 2.2 HTML model explorer (`CS-FEAT-EXPLORER`) — implemented (first version)

Two complementary surfaces, both served by the binary:

- **The *Library* button of the GUI** replaces the former *Examples* button (the `examples/` folder is now only
  for the CLI and the regression tests). It drops down the taxonomy of `taxonomy.json` — category → sub-category →
  model, with counts and a search box — and lists **verified models only**. Picking one opens the whole model
  folder (code, initial values, solver configuration, lookup tables, `.sol`) in the session, with *Back* to return
  to the previous model ([GUI §7.3](gui.md#73-library-models-a-model-is-a-folder)).
- **The dashboard at `/library/`** is the library's own `library.html` (generated by its `tools/build_index.py`):
  an *Explore* page following the taxonomy and sortable, filterable tables of **all** the models (blocked ones
  included, with the description of each gap), of the functions and procedures, and of the CoolSolve gaps. Every
  view has an address (`/library/#/models?status=blocked`, `/library/#CSL-0012`). When served by CoolSolve, each
  model page (blocked or not) has an **Open in CoolSolve** button — and one per variant file, e.g. the runnable
  `_coolsolve` variant of a blocked model — that opens `/?library=CSL-0012` in a **new tab with its own
  session**, so the model of the first tab is untouched. The README opens in the documentation viewer
  (`/docs/#library%2Fmodels%2F…%2FREADME.md`), whose banner also offers *Open in CoolSolve*. The documentation
  links to the dashboard (sidebar of `/docs/`), and the dashboard links to the documentation.
- **Routes**: `GET /api/v1/library/menu`, `POST /api/v1/library/open`, `GET /library/`, `GET /library/<path>`
  ([GUI §4.12](gui.md#412-model-library)).

**Include functions** is done (§2.3): in the GUI menu, a model that defines functions or procedures has a button
that copies `$INCLUDE <name>`; the model page of the dashboard shows the line with a *Copy* button.

Still to do from the original design: faceted search by level/kind/status/fluid in the GUI menu (the dashboard has
it), a thumbnail per model, *Copy code*, `coolsolve --library list / show / get` (`CS-FEAT-LIB-CLI`).

### 2.3 Importing functions and procedures from `.eescode` files (`CS-FEAT-IMPORT`) — implemented

One directive, on its own line, in the main program ([Language Reference §7](language_reference.md#include-functions-and-procedures-of-another-file)):

```ees
$INCLUDE hx_ees_function      "a library model, by its name"
$INCLUDE CSL-0332             "the same model, by its permanent ID"
$INCLUDE my_correlations      "my_correlations.eescode, in the folder of the model"
```

- **What is imported**: all the `FUNCTION`s and `PROCEDURE`s of the target; its main program (the
  demonstration equations of a library *function model*) is ignored. A library model is therefore a model and a
  function library at the same time; no `.lib` file is involved.
- **Resolution** (`include/coolsolve/include_resolver.h`): `<name>.eescode` of the **folder of the model**
  first — a file of the project takes precedence over a library model of the same name — then the library
  model of that **name or ID** (names are unique and IDs never change, so includes survive any re-organisation
  of the library folders; no path is accepted). The same rule in the CLI (folder of the model file, not the
  working directory) and in the GUI (folder of the file given on the command line, of the library model, or
  the files of an uploaded ZIP): a model includes the same files wherever it runs. An included library model
  resolves its own `$INCLUDE`s in its library folder and in the library only.
- **Nesting**: the `$INCLUDE`s of an included file are followed; cycles and the model including itself are
  errors; a file reached twice is imported once.
- **Conflicts** (warning `P011`): the model's own routine wins over an included one; a file of the project folder
  over a library model; otherwise the first `$INCLUDE` that defines the name.
- **Diagnostics**: an unknown name gives the closest library names; an error or warning of the included file is
  reported at the line of the directive with the file name and line.
- **Reproducibility**: the debug report (`report.md`) lists the included files (library ID and folder, or file
  name) and their routines; the LaTeX report names the included routines without their code; the ZIP bundle
  carries every included file next to the model, so that it runs on its own with the library version it was
  saved with (the precedence of the project folder makes the copies win).
- **GUI**: an include bar above the editor, only for a model that has an `$INCLUDE`, opens each included file in
  a new window ([GUI §7.5](gui.md#75-included-files-include)); the Library menu and the dashboard copy the
  `$INCLUDE` line of a model.
- **Native EES files** (`$INCLUDE file.lib`, `.txt`) are not read: the error asks to convert the file into a
  `.eescode` file of the folder (library workflow `T-FUNC`).
- **Implementation**: the parser (`src/parser.cpp`, `handleInclude`) parses each target with a parser of its own
  (its `$CONSTANT`s, `$IF`s and ranges resolved there), keeps its routines (`FunctionDefinition::includedFrom`)
  and inserts them after the directive once the model's own checks are done; `LibraryStore` supplies the text
  of library targets.

- **Lookup tables**: the tables `<stem>-<table>.csv` of the included file's folder come with its routines (a
  table of the model keeps its name, warning `L002`), so that a property library such as BrineProp
  (`CSL-0079`, `LOOKUP$('Units', …)`) works when included.

Not done (future work): *Export for EES* (`CS-FEAT-EXPORT-EES`, one file with the included routines written in),
editor auto-completion and quick-fix from the `functions` of `library.json` (*unknown function `cpbar`* →
"Include `cpbar_combustion_products`"), the native `.lib`/`.txt` files.

## 3. Features and implementation plan

| ID | Feature | Section | Priority |
|---|---|---|---|
| `CS-FEAT-LIB-EMBED` | Library snapshot embedded at build time, with version identity — **done**; run-time override (`--library-dir`) open | §2.1 | P1 |
| `CS-FEAT-EXPLORER` | HTML model explorer: taxonomy, search, facets, model pages, *Open* — **done** (Library menu + `/library/` dashboard), *Include functions* (copy `$INCLUDE <name>`) **done** | §2.2 | P1 |
| `CS-FEAT-IMPORT` | `$INCLUDE` of library models and `.eescode` files (all their functions and procedures) — **done**; native `.txt`/`.lib` not planned (convert them to `.eescode`) | §2.3 | P1 |
| `CS-FEAT-LIB-TEST` | Library regression test: solve every library model whose status is *verified* or *modified*, and every variant with a `.sol`, and compare with its `.sol` — **done** (`./coolsolve_tests "[library-regression]"`, §7); wiring into a CI open | – | P1 |
| `CS-FEAT-LIB-CLI` | `coolsolve --library list / show / get` | §2.2 | P2 |
| `CS-FEAT-EXPORT-EES` | *Export for EES*: flatten `$INCLUDE`s into a self-contained file (the ZIP bundle already carries the included files) | §2.3 | P2 |
| `CS-FEAT-PARAM-FILE` | Parametric-table file in the model folder (e.g. `<model>-parametric.csv`: one column per variable, one row per run), with **string columns** (fluid names) — needed to import EES parametric tables natively (`CS-GAP-PARAMETRIC`) | – | P2 |
| `CS-FEAT-DIAGRAM-IDEAL` | T-s / P-v / h-s diagrams without dome for ideal gases (`Air`, `N2`, `CO2`…) with the solved states — README figures of air-standard cycles, gas turbines and engines (meanwhile the library uses parametric sweep plots) | – | P2 |
| `CS-FEAT-PSYCHRO` | Psychrometric chart with the solved states of `AirH2O` models and PNG/SVG export — figures of the HVAC models (meanwhile parametric sweep plots) | – | P2 |
| `CS-FEAT-OVERLAY-STATES` | Let the user pick the variables of each state point in the Diagram tab (today: arrays or name suffixes), so that names such as `T_su_cp`, `h_ex_ev` can be drawn without adding equations | – | P2 |
| `CS-FEAT-METADATA` | "Save as library model": create the folder skeleton (README and `model.json` templates) from the current session | – | P3 |
| `CS-FEAT-PLOT-CLI` | Generate a diagram or a parametric plot from the CLI, to regenerate README figures when a model changes | – | P3 |

Suggested order of implementation:

1. **Snapshot and minimal explorer** (done) — allow-listed embedding,
   `library.json` identity, `/api/v1/library/menu` and `/library/`, explorer menu
   + dashboard + *Open*. The library is visible in every build.
2. **Imports** (done) — `$INCLUDE <name>` for library models and files of the
   model folder, *Include functions* buttons; the editor quick-fix is open.
   Library models then use `$INCLUDE` instead of copied functions.
3. **Tooling** — library regression in CI, CLI `--library`, *Export for EES*,
   run-time `--library-dir`, release procedure pinning the library tag.

## 6. Reporting a new gap

1. Check this register and [`ees_vs_coolsolve.csv`](ees_vs_coolsolve.csv).
2. Write a **minimal reproducer** (≤ 10 lines of EES code) and run it with the
   current CoolSolve build.
3. Add a row to §4 (missing/different feature) or §5 (bug), with a new ID
   `CS-GAP-<SHORT>` / `CS-BUG-<SHORT>`, the workaround used in the library and
   the IDs of the blocked models.
4. Reference the ID in the model's `model.json` (`missing_features`) and README.
5. When a gap is closed: update `ees_vs_coolsolve.csv`, replace the row by a
   one-line entry in §7 (ID, fix, commit) and re-test the blocked models (§9).

**Not gaps** (maintainer decisions; the library rewrites the model itself, decisions
D11/D12/D13/D14 of the library workflow): property calls with an input pair that CoolProp
does not support (`(T, h)`, `(s, v)`…) are rewritten with an equivalent supported
pair, external REFPROP calls (`CALL EES_REFPROP`) are rewritten as CoolProp
property calls, the NASA procedure (`CALL NASA(X$,T:cp,h,s)`) is rewritten as
ideal-gas property calls (`MolarMass(X$)*enthalpy(X$,T=T)`), and `$COMMON`
(variables of the main program shared with a FUNCTION/PROCEDURE body) is rejected
with an error that names the variables, which are passed as input arguments of the
routine and of each `CALL` instead, and string arrays (`Prod$[i]`, `U$[Pro]`) are rejected
with an error: the strings go into a lookup table, the model keeps the row number and reads
the string with `LOOKUP$('table', row, col)` (D14). Only a fluid or a mixture that CoolProp lacks is
a gap. Decisions of 2026-10-12: external table files (`.lkt`, `INTERPOLATE('file.txt',…)`) are not
read — every table is a CSV file in the model folder (`CS-GAP-LKT`); `StringPos` is not implemented
(`CS-GAP-STRINGPOS`); FUNCTION/PROCEDURE bodies are 100 % explicit, an implicit statement in a body is
an error and the model iterates explicitly or moves the equation to the main program
(`CS-BUG-IMPLICIT-PROC`); `INTEGRAL` keeps one integration variable per model
(`CS-GAP-INTEGRAL-MULTIVAR`, a possible future improvement). Such rows are kept in §4 with the priority *not a gap* so that importers find
the rule.
